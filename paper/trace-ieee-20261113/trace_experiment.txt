Abstract—Issue-driven regression testing requires translating
informal reports into executable behavioral checks. TRACE (Test
Reproduction through Analysis, Checks, and Evidence) adds
bounded extraction and validation of evidence-grounded issue
speciﬁcations before a DeepSeek coding agent generates native
test patches. We compare this workﬂow with a shared native-
test baseline on 26 assigned SWE-bench V eriﬁed instances using
the ofﬁcial SWT-Bench unit-test evaluator . Baseline resolves 16
instances and TRACE resolves 17; both apply all 26 patches.
The paired outcomes are 15 shared successes, two TRACE-only
successes, one baseline-only success, and eight shared failures.
Mean generation time increases from 93.45 to 127.09 seconds.
Six systematically selected case studies show that speciﬁcation
acceptance does not guarantee a valid regression oracle or com-
patibility with the ﬁxed repository. Parser attribution anomalies,
historical image limitations, diagnostic deviations, incomplete cost
accounting, and single-run variability constrain interpretation.
The observed one-instance gain is preliminary evidence rather
than a demonstrated general improvement.
Index Terms—regression testing, test generation, coding agents,
SWT-Bench, issue speciﬁcations
I. R ESEARCH QUESTION AND MOTIVATION
A regression test must encode the reported behavior, execute
in the project’s native suite, and distinguish buggy from
corrected code. An agent can produce a plausible assertion that
passes prematurely, fails for an unrelated reason, or becomes
invalid after a legitimate API change. SWT-Bench evaluates
repository-level generated tests against reference ﬁxes and
supplies complementary behavioral and coverage evidence [ 1],
[2].
We ask: Does evidence-grounded issue-speciﬁcation ex-
traction and validation improve DeepSeek’s issue reproduc-
tion success compared with direct report-to-test generation?
TRACE (Test Reproduction through Analysis, Checks, and
Evidence) hypothesizes that explicitly identifying a target,
trigger, observed behavior, expected behavior, and suggested
assertion will reduce unsupported assumptions. V alidation
is intended to ﬁlter analysis before generation; it does not
independently prove test correctness. Our contribution is a
bounded preprocessing workﬂow, preserved paired artifacts,
and an empirical examination of where formalized issue un-
derstanding helps or fails.
II. M ETHOD AND EXPERIMENTAL DESIGN
A. Two Workﬂows
Baseline. Our Python script, controller.py, reads the saved
issue description from report.txt. It passes that text unchanged
to mini-SWE-agent 2.4.6 [ 3] by calling agent.run(task). The
controller does not summarize or analyze the issue ﬁrst. mini-
SWE-agent combines the issue with the shared instructions
for writing regression tests and sends these messages to
DeepSeek. DeepSeek proposes shell commands to inspect
source code, read existing tests, write a test, and run it. mini-
SWE-agent executes those commands in a Docker container
containing the buggy repository, then sends their output and
exit status back to DeepSeek. This exchange repeats as the
model examines results and adjusts its test. DeepSeek selects
the actions; mini-SWE-agent carries them out and maintains
the conversation. The controller saves the ﬁnal submitted patch
and the conversation record.
TRACE. Before starting that same agent process, the con-
troller makes a separate request to DeepSeek to analyze only
the original issue. It asks for ﬁve items: the target function,
triggering input, observed behavior, expected behavior, and
a suggested assertion. Each item must include an exact sup-
porting quote from the issue; unknown information must be
marked null. Python checks that the response has the required
structure, that its quotes occur in the report, and that at least
one item contains usable information. A second, separate
DeepSeek request compares the extracted information with the
original issue description. It checks whether the issue supports
each item, whether any item contradicts the issue, and whether
important information was left out. These checks assess the
analysis, not the generated test.
If either check rejects the analysis, the controller sends
the errors back with the original issue and requests another
extraction. It permits three extraction attempts, each with a
review if the Python checks pass, for at most six preprocessing
calls. When analysis is accepted, the controller appends it to
the original issue and passes both to mini-SWE-agent. If all
attempts are rejected, it passes only the original issue and
records a fallback. Missing credentials and other operational
errors stop the run rather than triggering this fallback. The
agent then uses the same DeepSeek-driven inspection, test-
writing, execution, and submission process as the baseline.
The analysis requests and the agent’s generation requests

are separate conversations; only the accepted analysis text is
handed from one to the other.
The preserved run records support this procedure [ 5].
Both methods use the same native-test instructions, buggy
environment, and generation limits: 100 agent steps and a
nominal $0.50 agent budget, excluding TRACE preprocessing.
A ﬁnal call can exceed that budget. The agent’s submitted
patch is exported unchanged; non-submissions would export
empty predictions. Neither method receives the reference ﬁx
or evaluator-only results during generation or repair. Running
a test on buggy code supplies feedback, but does not establish
that it passes after the ﬁx. An automatic classiﬁer that dis-
tinguishes issue-related failures from syntax, import, or setup
errors is future work, not an implemented controller step.
The original agent conﬁguration asks for a standalone script
that reproduces the bug. For this experiment, both methods
instead receive the same instructions to add regression tests
to the repository’s existing test suite. Both also use a shell
setting that preserves a failing test runner’s exit status when
its output is piped through another command. These shared
changes make the outputs suitable for unit-test evaluation and
keep execution failures visible. The original conﬁguration ﬁle
is preserved; the controller applies these changes in memory
for each run. The comparison therefore measures the addition
of TRACE’s issue analysis to this shared unit-test workﬂow.
B. Assignment, Controls, and Evaluation
The ﬁxed assignment comprises 26 issues, 13 Easy
and 13 Hard, across 12 Python repositories. These
are historical assignment labels, not our measured dif-
ﬁculty classes. We retain SWE-bench V eriﬁed revision
c104f840cc67f8b6eec6f759ebc8b2693d585d4a. Both arms use
the same saved reports and paired environment references. For
each issue, we compare one baseline run with one TRACE
run. We reused three such pairs from the pilot phase; for
the remaining issues, we ran the baseline ﬁrst and TRACE
second. Conﬁguration and report hashes are checked. The
three pilot pairs recorded Docker image names rather than
unique image ﬁngerprints, limiting our ability to verify their
original image contents. We have one selected generation per
arm per instance, with earlier failures preserved. No explicit
generation seed was set. We did not repeat each method on
each issue, so we cannot determine how much the results
would change across repeated runs. The assignment is the
unit of analysis, not the number of test methods generated.
We record problems such as missing API credentials, network
errors, and environment setup failures separately from rejected
bug analyses. Fixing these setup problems does not permit
changing the experimental instructions. For each issue and
method, we use the generated patch identiﬁed in the saved run-
selection record. We do not compare evaluation scores from
earlier attempts and then choose the best-performing patch.
After test generation, we evaluate the saved patches
using the ofﬁcial SWT-Bench harness at commit
eee38624e36a1b39976fffa2bddbc4c3c754d293. The evaluator
uses unit-test mode with standard patch handling and coverage

III. R ESULTS
A. Success, Applicability, and Paired Outcomes
Table I reports ofﬁcial outcomes over all assignments.
Baseline resolves 16/26 instances (61.54%); TRACE resolves
17/26 (65.38%). Both apply 26/26 patches (100%). All 52
evaluation reports were produced—26 per method. No issues
were removed from the totals because of technical problems.
The evaluator reported no instance-level errors. Initial image
timeouts and admission failures were recovered before ﬁnal
evaluation. An exit code of zero indicates completed evalu-
ation, not that every reproduction succeeded. The inspected
harness requires additional fail-to-pass behavior relative to its
base comparison, preservation of base fail-to-pass behavior,
and no additional persistent or pass-to-fail failures. Therefore,
a patch can introduce a useful transitioning test yet remain
unresolved because another assertion introduces a lasting
regression. This stricter instance-level criterion explains some
disagreements better than counting isolated failing assertions.
The paired counts are 15 both succeed, one baseline only,
two TRACE only, and eight neither succeed (Table II). TRACE
gains Pytest 7432 and Django 15098 but loses Django 13344:
a net gain of one instance, or 3.85 percentage points. The
methods produced different success outcomes on only three
issues: two favored TRACE and one favored the baseline. This
small difference does not provide sufﬁcient statistical evidence
that either method performs better, nor does it establish that
they perform equally.
TRACE accepts 22 speciﬁcations and falls back on four is-
sues after three attempts each. These fallbacks remain TRACE
outcomes. Django 15098 is a TRACE-only success despite
fallback, so that gain cannot be credited directly to accepted

B. Coverage, Cost, and Runtime
We report the ofﬁcial ﬁeld coverage_delta_pred, a unitless
fraction over executable lines changed by the reference ﬁx
whose execution counts increase relative to the harness base
comparison. It is not whole-repository coverage. Arithmetic
means exclude unavailable values and are not weighted by
repository size or changed-line count. Overall means in-
clude all cases with coverage, regardless of success; success-
conditioned means use each method’s own successful subset
and therefore compare different subsets.
Sphinx 8721 has N/A coverage in both arms because the
harness ﬁnds no executable changed lines in its coverage
inputs. N/A is excluded, not replaced with zero. The exact
implementation and counts accompany the artifacts. Identi-
cal Django 11163 patches receive different coverage deltas,
demonstrating that these measurements can vary even when
submitted content matches.
Selected-run agent costs sum to $0.379071900 baseline
and $0.383181006 TRACE. TRACE additionally makes 69
preprocessing calls, recording 49,789 prompt and 173,755
completion tokens. The amounts above are agent-reported
costs for the selected runs only, not the total experiment cost.
We report the recorded preprocessing token usage separately
without assigning it a dollar amount. DeepSeek billing ex-
ports for October 18–November 16, 2026 show total charges
of $0.959975793 (approximately $0.96) across the exported
period. These charges are not limited to the selected 52
generation runs and cannot be separated reliably into baseline
and TRACE totals from the daily billing records alone. They
are reported separately, not added to the agent-reported costs,
because the records overlap. Mean controller generation time
rises by 33.64 seconds, approximately 36%, including TRACE
preprocessing but excluding image preparation. Evaluation
takes 57.10 minutes baseline and 25.83 minutes TRACE.
TRACE runs second and reuses comparison caches, so evalu-
ation timing is not evidence of workﬂow efﬁciency.
IV. T EST QUALITY ANALYSIS
Both the baseline and TRACE workﬂows instruct the
agent to include meaningful assertions and inspect failures
for syntax, import, setup, or issue-related causes. Execution
records support manual review, but we did not implement an
independent automatic checker for assertion quality or failure
relevance.
We choose six distinct cases systematically: sort full in-
stance IDs within each category, take the ﬁrst two shared
successes, ﬁrst two shared failures, then ﬁrst two disagree-
ments, without duplication. This yields Astropy 14508, Django
11163, Django 12155, Django 13513, Django 13344, and
Django 15098. No category shortfall occurs. Appendix A
discusses the issue, generated check, both execution states,
semantic relevance, and method implication for each.
The successful cases check clear expected behaviors: writ-
ing decimal numbers compactly in astronomy ﬁle headers
without truncating comments, and returning an empty dic-
tionary when no ﬁelds are requested. Both methods capture
these behaviors; additional structure offers no demonstrated
advantage there. The failures expose different weaknesses.
For Django 12155, both methods produced assertions that
exposed the indentation problem before the ﬁx. However, the
reference ﬁx removed a helper function that the existing test
module imported. This prevented the module from loading
afterward, so neither method demonstrated a passing test
on the ﬁxed code. For Django 13513, both methods added
tests checking that Django’s debug report hides an explicitly
suppressed exception. These tests passed before and after the
ﬁx because that behavior already worked. They did not exer-
cise the scenario addressed by the ofﬁcial ﬁx—an exception
without a traceback—and therefore did not reproduce the bug.
Accepted preprocessing does not guarantee compatibility or
discrimination.
The disagreements show why suite and parser evidence
matter. Django 13344 shows that validating an issue analysis
does not guarantee a correct test setup: TRACE reproduced a
similar symptom in a different middleware arrangement, but its
test still failed after the ﬁx. For Django 15098, both methods
generated URL tests that failed before the ﬁx and passed
afterward. However, the baseline also added a language-lookup
assertion that continued failing after the ﬁx, causing its overall
evaluation to fail. TRACE avoided that additional persistent
failure and succeeded. Because TRACE used the original
report after its analysis failed validation, this result does not
demonstrate a beneﬁt from the extracted analysis. Several
ofﬁcial transition labels do not align cleanly with raw test-
name lines; we report the ofﬁcial score and raw observations
separately rather than silently correcting either.
V. T HREATS TO VALIDITY
Several factors limit our ability to attribute the observed
improvement to TRACE. We selected one run per method for
each issue, reused three pilot pairs, and ran the baseline before
TRACE for the remaining issues. We did not measure variation
across repeated runs or changes in the hosted model. The same
model also extracted and reviewed the analysis, so both steps
could share the same misunderstanding.
Some recorded agent actions require additional review. Six
runs were ﬂagged for inspecting repository history. Other
diagnostic actions included a temporary plugin that changed
software behavior and stand-in code for missing dependencies.
For Sphinx 8621, the baseline agent created a temporary pytest

plugin that replaced the keyboard-formatting function in mem-
ory to try its own proposed ﬁx; passing tests under that plugin
were not results from the ofﬁcial reference ﬁx. For Sphinx
8638, the TRACE agent supplied a temporary replacement
for the missing roman dependency, whose toRoman() function
returned ordinary number strings instead of Roman numerals.
This allowed diagnostic tests to run, but did not reproduce the
real dependency’s behavior. Although the submitted patches
contain only test changes, this does not prove that every action
taken during generation followed the experiment’s restrictions.
The reported results depend on which tests the evaluator
runs and how it reads their output. Some test names could
not be matched between the before-ﬁx and after-ﬁx logs, and
some recorded transitions belonged to existing tests rather than
newly generated ones. These issues can affect the reported suc-
cess counts. Coverage measures execution of lines changed by
the reference ﬁx, not whether an assertion correctly represents
the issue. We report the ofﬁcial results for all 26 issues and
document discrepancies found in the raw logs. For three pilot
pairs, we recorded Docker image names but not unique image
ﬁngerprints, so we cannot fully verify their original contents.
Our ﬁndings apply to a small set of assigned Python issues.
The assignment’s Easy and Hard labels and TRACE’s one-
issue advantage do not establish how either method would
perform on other projects. Provider billing totals are available
for the exported period, but the records do not separate charges
by workﬂow or selected run, so they cannot establish which
method is more cost-effective.
A follow-up study should decide how many repeated runs
to perform and how to handle violations of the experiment’s
rules before reviewing results. Human reviewers could also
independently check whether each test captures the reported
behavior and whether its failure comes from the bug rather
than an environment problem. Measuring how often reviewers
agree would provide an additional check beyond DeepSeek
reviewing its own analysis.
VI. C ONCLUSION
TRACE achieves 17/26 ofﬁcial successes versus 16/26 for
the baseline, with universal patch applicability and increased
mean generation time. The paired evidence supports a modest
observed difference, not a dependable superiority claim. Future
work should repeat generation under recorded seeds where
supported, isolate preprocessing through controlled ablations,
audit raw-to-parsed transitions, and add a shared quality
checker for issue relevance and setup failures. Such a checker
should initially measure both methods without evaluator-
guided repair. Any later sensitivity analysis must accompany
the full assigned-set results rather than discard inconvenient
cases.

APPENDIX A
SIX DISTINCT CASE STUDIES
The cases below use the selection rule in Section IV . “Suc-
cess” denotes the ofﬁcial instance-level result. Raw pre/post
observations are reported separately where parser attribution
differs. Source paths and complete transition sets are indexed
in evidence.json beside the paper.
We assess TRACE’s generated tests using four properties:
P1, meaningful assertions : explicitly check an expected out-
come; P2, issue-related failure: fail on buggy code because of
the reported problem, not a typo, import error, or setup failure;
P3, passes after the ﬁx : the same generated test executes and
passes after the reference ﬁx; and P4, requirement alignment:
the test setup and assertions represent the behavior requested in
the issue. These are retrospective assessments from submitted
patches and saved execution evidence, not outputs of an
implemented automatic quality checker. A passing post-ﬁx
test alone does not establish issue reproduction. “Partial”
indicates that only part of the reported scenario is represented;
“not established” indicates insufﬁcient evidence, rather than a
conﬁrmed negative result.
A. Shared Success: Astropy 14508
Issue. FITS (Flexible Image Transport System) is a ﬁle
format used in astronomy. Its header stores metadata in 80-
character records called cards, containing a keyword, a value,
and an optional comment. The HIERARCH convention al-
lows keyword names longer than the usual eight characters,
while retaining the 80-character record limit. 1 In this issue,
a decimal value is written with unnecessarily many digits,
leaving too little space for the comment and causing it to be cut
off. Generated checks. Both methods construct the reported
card using the value 0.009125 and compare its serialized
representation with the compact expected string. Baseline
additionally checks the stored value and comment. Before.
Both new tests fail with a V erifyWarning about comment
truncation. After .Each passes, and each ofﬁcial report records
one added fail-to-pass test without added persistent or pass-
to-fail failures. Relevance. The tests check that the number is
written compactly and the full comment is preserved, directly
matching the problem described in the bug report. Implica-
tion. Both methods ﬁnd an effective native oracle; TRACE’s
accepted speciﬁcation does not produce an observable success
advantage.

C. Shared Failure: Django 12155
Issue. When a docstring starts with text rather than a blank
line, Django leaves extra indentation on later lines. This can
cause errors when the documentation is displayed. Generated
checks. Both workﬂows add assertions checking that indenta-

Exposing the bug before the ﬁx is only part of a successful

Issue. Django does not correctly recognize language codes
that specify both a writing system and a region. For example,
en-latn-us means English, written using the Latin alphabet, for
the United States. A valid web address using this language
preﬁx can return a 404 Not Found response instead of the
requested page. Generated checks. Both workﬂows add tests
checking that the language-preﬁxed address works and that
Django recognizes the language code. The baseline adds a
language-lookup assertion to an existing test. TRACE creates
a separate lookup test that also checks codes with mixed
uppercase and lowercase letters. Before generation, TRACE
tries three times to extract an analysis that passes validation.
None is accepted, so the agent receives only the original report,
just as in the baseline. This run still counts as a TRACE result
and includes the unsuccessful analysis attempts. Before. Both
URL checks fail, and each method’s lookup assertion fails.
After . Both URL checks pass. Baseline’s modiﬁed existing
lookup test still fails; TRACE’s new lookup method is logged
as passing. Both suites retain additional existing failures/errors.

inspection remains a separate limitation.

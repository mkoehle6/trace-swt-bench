Abstract—Issue-driven regression testing requires translating
informal reports into executable behavioral checks. TRACE (Test
Reproduction through Analysis, Checks, and Evidence) adds
bounded extraction and validation of evidence-grounded issue
speciﬁcations before a DeepSeek-Flash-powered coding agent
generates native test patches. We compare this workﬂow with
a shared native-test baseline on 26 assigned SWE-bench V eriﬁed
instances using the ofﬁcial SWT-Bench unit-test evaluator . Base-
line succeeds on 16 instances and TRACE on 17; all 26 patches
from each workﬂow apply successfully. The paired outcomes are
15 shared successes, two TRACE-only successes, one baseline-
only success, and eight shared unsuccessful outcomes. Mean
generation time increases from 93.45 to 127.09 seconds. Six sys-
tematically selected case studies illustrate that issue-speciﬁcation
acceptance does not guarantee a test that correctly checks the
reported behavior or compatibility with the ﬁxed repository.
Test-name attribution discrepancies, incomplete historical image
records, diagnostic deviations from the protocol, incomplete
per-method cost accounting, and single-run variability limit
interpretation. The observed one-instance gain is preliminary
evidence rather than a demonstrated general improvement.
Index Terms—regression testing, test generation, coding agents,
SWT-Bench, issue speciﬁcations
I. R ESEARCH QUESTION AND MOTIVATION
A regression test must encode the reported behavior, execute
in the project’s native suite, and distinguish buggy from
corrected code. An agent can produce a plausible assertion that
passes prematurely, fails for an unrelated reason, or becomes
invalid after a legitimate API change. SWT-Bench evaluates
repository-level generated tests against reference ﬁxes and
supplies complementary behavioral and coverage evidence [ 1],
[2].
We use DeepSeek-Flash for test generation in both work-
ﬂows. We ask: Does evidence-grounded issue-speciﬁcation
extraction and validation improve DeepSeek-Flash’s issue
reproduction, as measured by ofﬁcial SWT-Bench instance-
level success, compared with direct report-to-test generation?
TRACE (Test Reproduction through Analysis, Checks, and
Evidence) is motivated by the hypothesis that explicitly iden-
tifying a target, trigger, observed behavior, expected behavior,
and suggested assertion will reduce unsupported assumptions.
We measure reproduction success, not the number of unsup-
ported assumptions, so the proposed mechanism is not directly
tested. V alidation is intended to ﬁlter the issue speciﬁcation

II. M ETHOD AND EXPERIMENTAL DESIGN
A. Two Workﬂows
In this paper, “DeepSeek” means DeepSeek-Flash; recorded
provider identiﬁers appear in Appendix D.
Baseline. Our Python script, controller.py, reads the saved
issue description from report.txt. It passes that text unchanged
to mini-SWE-agent 2.4.6 [ 3] by calling agent.run(task). The
controller does not summarize or analyze the issue ﬁrst. mini-
SWE-agent combines the issue with the shared instructions
for writing regression tests and sends these messages to
DeepSeek. DeepSeek proposes shell commands to inspect
source code, read existing tests, write a test, and run it. mini-
SWE-agent executes those commands in a Docker container
containing the buggy repository, then sends their output and
exit status back to DeepSeek. This exchange repeats as the
model examines results and adjusts its test. DeepSeek selects
the actions; mini-SWE-agent carries them out and maintains
the conversation. The controller saves the ﬁnal submitted patch
and the conversation record.
TRACE. Before starting that same agent process, the con-
troller makes a separate request to DeepSeek to analyze only
the original issue. It asks for ﬁve items: the target function,
triggering input, observed behavior, expected behavior, and
a suggested assertion. Each known item must include an
exact supporting quote from the issue; an unknown item
and its evidence must both be marked null. Python checks
that the response has the required structure, that its quotes
occur in the report, and that at least one item contains usable
information. A second, separate DeepSeek request compares
the extracted information with the original issue description.
It checks whether the issue supports each item, whether any
item contradicts the issue, and whether important information
was left out. These checks assess the issue speciﬁcation, not
the generated test.
If either check rejects the issue speciﬁcation, the controller
sends the errors back with the original issue and requests
another extraction. It permits up to three extraction attempts;
each attempt that passes the Python checks is followed by
a review, giving at most six preprocessing requests. When

an issue speciﬁcation is accepted, the controller appends it
to the original issue and passes both to mini-SWE-agent. If
all attempts are rejected, it passes only the original issue and
records a fallback. Missing credentials and other operational
errors stop the run rather than triggering this fallback. The
agent then uses the same DeepSeek-driven inspection, test-
writing, execution, and submission process as the baseline.
The speciﬁcation-extraction and review requests are separate
from the agent’s generation conversation; only the accepted
issue speciﬁcation is handed from one to the other.
The course guidelines require a same-model workﬂow com-
parison and ofﬁcial unit-test evaluation [ 4]. The preserved run
records support this procedure [ 5]. Both methods use the same
native-test instructions, buggy environment, and generation
limits: 100 agent steps and a nominal $0.50 agent budget,
excluding TRACE preprocessing. A ﬁnal model request can
take spending above that nominal limit. The agent’s submitted
patch is exported unchanged. All 52 selected runs submit-
ted patches, so no empty predictions occurred in the ﬁnal
evaluated set; the exporter retains non-submissions as empty
predictions when they occur. Neither method receives the
reference ﬁx or evaluator-only results during generation or
repair. Running a test on buggy code supplies feedback, but
does not establish that it passes after the ﬁx. An automatic
classiﬁer that distinguishes issue-related failures from syntax,
import, or setup errors is future work, not an implemented
controller step.
The original agent conﬁguration asks for a standalone script
that reproduces the bug. For this experiment, both methods
instead receive the same instructions to add regression tests
to the repository’s existing test suite. Both also enable Bash’s
pipefail option, which preserves a failing test runner’s exit
status when its output is piped through another command.
These shared changes make the outputs suitable for unit-test
evaluation and keep execution failures visible. The original
conﬁguration ﬁle is preserved; the controller applies these
changes in memory for each run. The comparison therefore
measures the addition of TRACE’s issue speciﬁcation to this
shared unit-test workﬂow.
B. Assignment, Controls, and Evaluation
The ﬁxed assignment comprises 26 issues, 13 Easy
and 13 Hard, across 12 Python repositories. These
are historical assignment labels, not our measured dif-
ﬁculty classes. We use SWE-bench V eriﬁed revision
c104f840cc67f8b6eec6f759ebc8b2693d585d4a. Both arms use
the same saved reports and the same Docker image for each
pair. For each issue, we compare one baseline run with one
TRACE run. We reused three such pairs from the pilot phase;
for the remaining issues, we ran the baseline ﬁrst and TRACE
second. Conﬁguration and report hashes are checked. The
three pilot pairs recorded Docker image names rather than
unique image ﬁngerprints, limiting our ability to verify their
original image contents. We have one selected generation per
arm per instance, with earlier failed attempts preserved. No
explicit generation seed was set. We did not repeat each
method on each issue, so we cannot determine how much
the results would change across repeated runs. Each assigned
instance is the unit of analysis, not each generated test method.
We record problems such as missing API credentials, network
errors, and environment setup failures separately from rejected
issue speciﬁcations. Fixing these setup problems does not
permit changing the experimental instructions. For each issue
and method, we use the generated patch identiﬁed in the saved
run-selection record. We do not compare evaluation scores
from earlier attempts and then choose the best-performing
patch.
After test generation, we evaluate the saved patches
using the ofﬁcial SWT-Bench harness at commit
eee38624e36a1b39976fffa2bddbc4c3c754d293. The evaluator
uses unit-test mode with standard patch handling and
coverage collection enabled. It runs up to two evaluation jobs
at once, with a 30-minute timeout for each execution. Both
methods use identical evaluation settings. Dataset reference
ﬁelds and evaluation outputs remain in an evaluation-only
directory. All 26 assigned instances remain in the success-
rate and patch-applicability denominators for each method.
After infrastructure failures, recovery reuses unchanged
environment-build recipes or predictions and preserves
unsuccessful attempts. Candidates are not selected based on
evaluation outcomes.
III. R ESULTS
A. Success, Applicability, and Paired Outcomes
Table I reports ofﬁcial outcomes over all assignments. Base-
line succeeds on 16/26 instances (61.54%); TRACE succeeds
on 17/26 (65.38%). Both methods have 26/26 applicable
patches (100%): applicability means that the submitted patch
applies cleanly to the repository. Table III in Appendix B
lists every paired outcome and coverage value. Appendix C
provides reproducibility details, and Appendix D records team
contributions and AI-tool use. All 52 evaluation reports were
produced—26 per method. No issues were removed from the
totals because of technical problems. The evaluator reported no
instance-level errors. Initial image timeouts and setup-check
failures were resolved before ﬁnal evaluation.
An evaluator exit code of zero indicates completed eval-
uation, not that every reproduction succeeded. The harness
compares runs with the generated patch against a base com-
parison without that patch. It requires (i) additional fail-to-
pass tests, (ii) preservation of the base comparison’s fail-
to-pass tests, and (iii) no additional tests that fail in both
versions or change from passing to failing. Therefore, a patch
can introduce a useful fail-to-pass test yet be unsuccessful
because another assertion introduces a lasting regression. This
stricter instance-level criterion explains some disagreements
better than counting isolated failing assertions.
The paired outcomes are 15 instances where both succeed,
one where only the baseline succeeds, two where only TRACE
succeeds, and eight where neither succeeds (Table II). TRACE
succeeds where the baseline does not on pytest 7432 and
Django 15098; the baseline alone succeeds on Django 13344.

The net difference is one instance, or 3.85 percentage points.
The methods produced different success outcomes on only
three issues: two favored TRACE and one favored the baseline.
An exact two-sided McNemar test on the two TRACE-only
and one baseline-only successes gives p = 1 .0. This small
difference does not provide sufﬁcient statistical evidence that
either method performs better, nor does it establish that they
perform equally.
TRACE accepts 22 issue speciﬁcations and falls back after
three attempts on Django 15098, Django 16631, Sphinx 8551,
and Django 13810. These fallbacks remain TRACE outcomes.
Django 15098 is a TRACE-only success despite fallback,
so that gain cannot be credited directly to the accepted
issue speciﬁcation. Django 11163 and Flask 5014 have byte-
identical baseline/TRACE patches. TRACE accepts the issue
speciﬁcation for Django 13344 on its second extraction at-
tempt, without fallback. Overall counts therefore describe the
complete workﬂow, including fallback and sampling variation,
rather than establishing whether speciﬁcation extraction caused
the difference.
B. Coverage, Cost, and Runtime
We report the ofﬁcial ﬁeld coverage_delta_pred, the fraction
of executable lines changed by the reference ﬁx whose execu-
tion counts increase relative to the harness base comparison.
This fraction is unitless. It is not whole-repository coverage.
Arithmetic means exclude unavailable values and are not
weighted by repository size or changed-line count. Overall
means include all cases with available coverage, regardless
of success. Success-only means use each method’s successful
cases with available coverage, so the two methods are averaged
over different subsets.
Sphinx 8721 has N/A coverage in both arms because the
harness ﬁnds no executable changed lines in its coverage
inputs. N/A is excluded, not replaced with zero. The per-
instance coverage values and aggregation counts are indexed in
evidence.json; the metric implementation is in src/grading.py
at the recorded SWT-Bench harness commit. A zero coverage
delta means that no counted changed line has a positive
execution-count increase relative to the base comparison; it
does not mean that those lines were never executed. Success
uses test outcomes rather than this coverage measure, so
TRACE can succeed on Django 15098 and SymPy 24539 with
zero delta. Baseline Django 15098 also has zero delta, but is
unsuccessful. Identical Django 11163 patches receive different
coverage deltas, showing that these measurements can vary
even when submitted content matches.
Agent-reported costs for the selected runs total $0.379072
for baseline and $0.383181 for TRACE. TRACE additionally
makes 69 preprocessing requests, recording 49,789 input and
173,755 output tokens. These costs exclude preprocessing and
are not the total experiment cost. We report the recorded
preprocessing token usage separately without assigning it a
dollar amount.
DeepSeek billing exports for October 18–November 16,
2026 show total charges of $0.959976 (rounded) across the
exported period. These charges are not limited to the selected
52 generation runs and cannot be separated reliably into base-
line and TRACE totals from the daily billing records alone.
They are reported separately, not added to the agent-reported
costs, because adding them would double-count charges for
the selected runs.
Mean generation time recorded by the controller increases
by 33.64 seconds, approximately 36%, including TRACE pre-
processing but excluding image preparation. Evaluation takes
57.10 minutes for baseline and 25.83 minutes for TRACE.
TRACE runs second and reuses comparison caches, so evalu-
ation timing is not evidence of workﬂow efﬁciency.
IV. T EST QUALITY ANALYSIS
Both the baseline and TRACE workﬂows instruct the
agent to include meaningful assertions and inspect failures
for syntax, import, setup, or issue-related causes. Execution
records support manual review, but we did not implement an
independent automatic checker for assertion quality or failure
relevance.
We choose six distinct cases systematically: sort full in-
stance IDs within each category, take the ﬁrst two shared
successes, ﬁrst two shared failures, then ﬁrst two disagree-
ments, without duplication. This yields Astropy 14508, Django
11163, Django 12155, Django 13513, Django 13344, and
Django 15098. Each category contains at least two cases, so no
additional cases are needed. Appendix A discusses the issue,
generated check, both execution states, semantic relevance,
and method implication for each.
The successful cases check clear expected behaviors: writ-
ing decimal numbers compactly in astronomy ﬁle headers

without truncating comments, and returning an empty dic-
tionary when no ﬁelds are requested. Both methods capture
these behaviors; additional structure offers no demonstrated
advantage there. The failures expose different weaknesses.
For Django 12155, both methods produced assertions that
exposed the indentation problem before the ﬁx. However, the
reference ﬁx removed a helper function that the existing test
module imported. This prevented the module from loading
afterward, so neither method demonstrated a passing test on
the ﬁxed code. For Django 13513, both methods added tests
checking that Django’s debug report hides an earlier exception
explicitly suppressed with raise...fromNone. These tests passed
before and after the ﬁx because that behavior already worked.
They did not exercise the scenario addressed by the ofﬁcial
ﬁx—an exception without a traceback—and therefore did not
reproduce the bug. An accepted issue speciﬁcation does not
guarantee compatibility with the ﬁxed code or the ability to
distinguish buggy from ﬁxed code.
The disagreement cases illustrate that an added persistent
failure can make an instance unsuccessful even when new
tests go from failing to passing. They also show that parsed
test labels can differ from raw execution logs. Django 13344
shows that validating an issue speciﬁcation does not guarantee
a correct test setup: TRACE reproduced a similar symptom in
a different middleware arrangement, but its test still failed after
the ﬁx. For Django 15098, both methods generated URL tests
that failed before the ﬁx and passed afterward. However, the
baseline also added a language-lookup assertion that continued
failing after the ﬁx, causing its overall evaluation to fail.
TRACE avoided that additional persistent failure and suc-
ceeded. Because TRACE used the original report after its issue
speciﬁcation failed validation, this result does not demonstrate
a beneﬁt from the extracted issue speciﬁcation. Several ofﬁcial
transition labels do not align cleanly with raw test-name lines;
we report the ofﬁcial score and raw observations separately
rather than silently correcting either.
V. T HREATS TO VALIDITY
Several factors limit our ability to attribute the observed
improvement to TRACE. We selected one run per method for
each issue, reused three pilot pairs, and ran the baseline before
TRACE for the remaining issues. We did not measure variation
across repeated runs or changes in the hosted model. The same
model also extracted and reviewed the issue speciﬁcation, so
both steps could share the same misunderstanding.
Some recorded agent actions require additional review. Six
selected runs were ﬂagged for inspecting repository history:
baseline on Django 13513, Django 15098, and Django 16631;
TRACE on Seaborn 3187, Sphinx 8548, and Sphinx 8638.
These are command-review ﬂags, not proof that a reference
ﬁx was accessed or used. Other diagnostic actions included a
temporary plugin that changed software behavior and stand-
in code for missing dependencies. For Sphinx 8621, the
baseline agent created a temporary pytest plugin that replaced
the keyboard-formatting function in memory to try out its
own proposed ﬁx; passing tests under that plugin were not
results from the ofﬁcial reference ﬁx. For Sphinx 8638, the
TRACE agent supplied a temporary replacement for the miss-
ing roman dependency, whose toRoman() function returned
ordinary number strings instead of Roman numerals. This
allowed diagnostic tests to run, but did not reproduce the
real dependency’s behavior. The submitted patches contain
only test changes, but the patches alone do not establish
that all actions during generation followed the experiment’s
restrictions.
The reported results depend on which tests the evaluator
runs and how it reads their output. Some test names could
not be matched between the before-ﬁx and after-ﬁx logs, and
some recorded before/after transitions belonged to existing
tests rather than newly generated ones. These issues can affect
the reported success counts. Coverage measures execution of
lines changed by the reference ﬁx, not whether an assertion
correctly represents the issue. We report the ofﬁcial results for
all 26 issues and document discrepancies found in the raw
logs. For three pilot pairs, we recorded Docker image names
but not unique image ﬁngerprints, so we cannot fully verify
their original contents.
Our ﬁndings apply to a small set of assigned Python issues.
Neither the Easy/Hard labels nor TRACE’s one-instance ad-
vantage indicates how either method would perform on other
projects. Provider billing totals are available for the exported
period, but the records do not separate charges by workﬂow or
selected run, so they cannot establish which method is more
cost-effective.
A follow-up study should specify the number of repeated
runs and how rule violations will be handled before reviewing
any results. Human reviewers could also independently check
whether each test captures the reported behavior and whether
its failure comes from the bug rather than an environment
problem. Measuring how often reviewers agree would provide
an additional check beyond DeepSeek reviewing its own issue
speciﬁcation.
VI. C ONCLUSION
TRACE achieves 17/26 ofﬁcial successes versus 16/26 for
the baseline, with 100% patch applicability and increased
mean generation time. The paired evidence supports a modest
observed difference, not a reliable advantage for TRACE.
Future work should repeat generation under recorded seeds
where supported, compare extraction with and without review,
check how raw test results are converted into parsed transi-
tions, and add a shared quality checker for issue relevance
and setup failures. Such a checker should initially assess both
methods without using evaluator-only results to repair tests.
Any later analysis of how the ﬁndings change under alternative
assumptions should supplement the full assigned-set results
rather than discard unfavorable cases.

APPENDIX A
SIX DISTINCT CASE STUDIES
The cases below use the selection rule in Section IV. “Suc-
cess” denotes the ofﬁcial instance-level result. Raw before-ﬁx
and after-ﬁx observations are reported separately when the log
parser assigns results to different test names. Source paths and
complete transition sets are indexed in evidence.json beside the
paper.
We assess TRACE’s generated tests using four properties:
P1, meaningful assertions : the test explicitly checks an
expected outcome; P2, issue-related failure : the test fails
on buggy code because of the reported problem, not a typo,
import error, or setup failure; P3, passes after the ﬁx : the
same test executes and passes after the reference ﬁx; and P4,
requirement alignment : the test uses a setup and assertions
that represent the behavior requested in the issue. These are
retrospective assessments from submitted patches and saved
execution evidence, not outputs of an implemented automatic
quality checker. P1–P4 are scored only for TRACE to assess
the proposed workﬂow; baseline behavior is described for
comparison but was not separately scored with this rubric.
A passing post-ﬁx test alone does not establish issue re-
production. “Partial” indicates that only part of the reported
scenario is represented; “not established” indicates insufﬁcient
evidence, rather than a conﬁrmed negative result.
A. Shared Success: Astropy 14508
Issue. FITS (Flexible Image Transport System) is a ﬁle
format used in astronomy. Its header stores metadata in 80-
character records called cards, containing a keyword, a value,
and an optional comment. The HIERARCH convention allows
keyword names longer than the usual eight characters, while
retaining the 80-character record limit. 1

many digits, leaving too little space for the comment and
causing it to be cut off. Generated checks. Both methods
construct the reported card using the value 0.009125 and
compare its serialized representation with the compact ex-
pected string. Baseline additionally checks the stored value and
comment. Before. Both new tests fail with a V erifyWarning
about comment truncation. After . Each passes, and each
ofﬁcial report records one added fail-to-pass test without added
persistent or pass-to-fail failures. Relevance. The tests check

is preserved, directly matching the problem described in the

C. Shared Failure: Django 12155
Issue. When a docstring starts with text rather than a blank
line, Django leaves extra indentation on later lines. This can
cause errors when the documentation is displayed. Generated
checks. Both workﬂows add assertions checking that indenta-
tion is removed correctly and that the docstring is split into
the expected parts. TRACE also checks that the displayed
documentation does not contain a formatting-error message
from docutils, the documentation-processing library. Before.
The saved execution logs show two new assertion failures
for each workﬂow. These failures expose incorrect indentation
handling; TRACE also detects a documentation-formatting
error. After . The reference ﬁx removes the trim_docstring
helper, but the existing test module still imports it. That import
fails before the runner can execute the newly added tests.
The evaluator therefore cannot match those tests across the
before-ﬁx and after-ﬁx runs, records no added fail-to-pass
tests, and marks both workﬂows unsuccessful. Relevance. The
assertions target the reported problem, but the tests rely on a
helper that is no longer available after the ﬁx. Implication.
Exposing the bug before the ﬁx is only part of a successful
reproduction: the same test must also run and pass on the ﬁxed
code. Neither workﬂow demonstrated that here. V alidating
the issue speciﬁcation did not prevent this test-compatibility
problem, and the reference ﬁx was not available to the agents
during generation.

P2 met for the observed new failures: retained indentation

raise...fromNone to request that the earlier exception not be
displayed. They then check the exception information col-
lected for the debug report. Before and after . The new tests
pass on both buggy and ﬁxed code because Django already
handles the particular scenario they check. Neither workﬂow
produces a new test that fails before the ﬁx and passes
afterward, so both receive an unsuccessful result. A separate
failure in an existing debug-template test is not a failure of
these newly generated checks. Relevance. The tests address
exception hiding, which is related to the report, but miss the
speciﬁc case addressed by the ofﬁcial ﬁx: an exception without
a traceback, meaning that it carries no record of where it was
raised. This detail was identiﬁed in our post-hoc review of
the evaluation results and was not supplied to the agents for
generation or repair. Implication. A test can contain sensible
assertions about the right general topic yet fail to exercise
the actual bug. TRACE’s accepted issue speciﬁcation did not
prevent that outcome. Both methods receive a coverage delta
of 0.647059 for this issue despite failing to reproduce it;
executing relevant code is not the same as checking the broken
behavior. The baseline agent also inspected repository history,
which requires review against the experiment’s restrictions.
TRACE quality assessment. P1 met: explicit assertions
check the exception information. P2 not met: the generated
tests pass on buggy code instead of exposing the bug. P3
met as an execution observation: the tests pass after the ﬁx;
because they also pass before it, this does not show successful
reproduction. P4 partial: the tests check related exception-
hiding behavior but omit the exception-without-a-traceback
scenario. They therefore cannot distinguish the buggy version
from the ﬁxed version.
E. Disagreement: Django 13344
Issue. Middleware is code that processes a web request or
response around a Django view. In the reported bug, the ﬁrst
middleware’s process_response() method receives a coroutine,
an asynchronous operation that still needs to be awaited,
instead of a completed HttpResponse.
Generated checks. Both workﬂows add a helper middle-
ware that records the object passed to process_response().
They then assert that the recorded object is an HttpResponse.
The baseline places its helper before Django’s existing
SecurityMiddleware, following the report’s example. TRACE
instead places its helper before a new async-only middleware
written by the agent. TRACE chose that setup after temporary
experiments showed that it produced the reported coroutine
symptom. Its issue speciﬁcation had been accepted on the
second extraction attempt, so this was not a fallback run.
Listing 3. Expected response type checked by both workﬂows, simpliﬁed.
self.assertIsInstance(response, HttpResponse)
Before. Both new tests fail because their recording helpers
receive a coroutine rather than an HttpResponse. After . The
baseline test passes after the reference ﬁx. TRACE’s test still
receives a coroutine and fails. The ofﬁcial evaluator therefore
marks the baseline successful and TRACE unsuccessful.
Reading the evaluation records. The baseline’s raw logs
show the new test failing before the ﬁx and passing afterward.
However, the evaluator’s log parser labels an existing test,
test_get_asgi_application, as the fail-to-pass entry and cannot
match the new test name between runs. We report the ofﬁcial
outcome while noting that its test-name attribution differs from
the raw logs.
Relevance. Both tests check the expected response type, but
they use different middleware setups. TRACE reproduced a
similar symptom without demonstrating that its setup exercised
the same underlying bug. Its continued failure after the ﬁx does
not by itself identify the precise cause. Implication. Checking
that the issue speciﬁcation is supported by the report does not

guarantee that the agent will build a faithful executable test.
The response assertion and the surrounding setup both matter.
TRACE quality assessment. P1 met: the test explicitly
checks for an HttpResponse. P2 not established: it fails with
the reported symptom, but the evidence does not establish that
the same underlying bug caused it. P3 not met: the test still
fails after the reference ﬁx. P4 partial: the expected response
type matches the report, but the custom middleware setup
differs from its example and is not shown to reproduce the

F . Disagreement: Django 15098
Issue. Django does not correctly recognize language codes
that specify both a writing system and a region. For example,
en-latn-us means English, written using the Latin alphabet, for
the United States. A valid web address using this language
preﬁx can return a 404 Not Found response instead of the
requested page. Generated checks. Both workﬂows add tests
checking that the language-preﬁxed address works and that
Django recognizes the language code. The baseline adds a
language-lookup assertion to an existing test. TRACE creates
a separate lookup test that also checks codes with mixed
uppercase and lowercase letters. Before generation, TRACE
tries three times to extract an issue speciﬁcation that passes
validation. None is accepted, so the agent receives only the
original report, just as in the baseline. This run still counts
as a TRACE result. Its recorded generation time includes the
unsuccessful preprocessing attempts, and their API charges
contribute to workﬂow spending; the agent-only cost ﬁgures
exclude those requests. Before. The URL tests and language-
lookup assertions generated by both workﬂows fail. After .
Both URL checks pass. The existing lookup test modiﬁed by
baseline still fails, while TRACE’s new lookup test passes in
the raw log. Both suites retain additional existing failures or
errors. The ofﬁcial baseline report records two added fail-to-
pass entries but also an additional persistent failure relative
to base, yielding an unsuccessful result. TRACE records three
added fail-to-pass entries without an added persistent failure
and succeeds. The parser cannot match TRACE’s new lookup
test name between runs, even though the raw after-ﬁx log
records it as passing. Relevance. The URL tests directly check
the reported behavior, while the additional language-lookup
assertions check different aspects of language-code handling.
Implication. The harness checks whether the generated patch
introduces additional failures relative to its base comparison,
not simply whether a new test changes from failing to pass-
ing. This TRACE-only success occurred without an accepted
issue speciﬁcation and therefore cannot demonstrate that an
accepted issue speciﬁcation caused the gain. Baseline’s history
inspection remains a separate limitation.
TRACE quality assessment. P1 met: explicit checks cover
language-preﬁxed URLs and language lookup. P2 met for
the observed generated checks: buggy execution fails on the
language-code behavior rather than a syntax or setup error.
P3 met in the inspected raw logs: the URL checks and new
lookup method pass after the ﬁx; parsed attribution of the
lookup method remains uncertain. P4 met for the reported lan-
guage/script/region behavior. TRACE receives ofﬁcial success,
but because preprocessing fell back to the original report, these
properties cannot be credited to an accepted issue speciﬁcation.
